# 孤山掠影

自驾×徒步混合行程规划桌面应用(自用)。

**一句话**:选区域(川西、滇西北等 17 个环线区域)+ 出发站 + 日期 + 天数 + 人数 → 一屏得到:往返火车实时票价(12306,支持在同次查询的候选车次间一键切换,夜车自动优先卧铺)、逐日自驾里程/油费/过路费(高德,地图按真实驾车路线画线,油费优先当日分省实价)、徒步日安排(私有线路库,标注当日天气宜否、错季提醒,天气差时有确定性改期/休整建议)、16 天天气窗口,以及含住宿/餐饮估算的预算表(合计+人均,火车票/门票按人头计)。行程自带行前装备清单(由线路字段与天气推导),可导出 Markdown 或打印带走。所有价格可溯源(存档在 `data/trips/`),缺失响亮报错,绝不编造。

- **行程规划**:生成行程、换车次(零新请求)、看徒步日天气与区域路况提示;去程太晚到/回程太早发会挂出衔接警告;无票时可显式点击查邻日车次参考。
- **路线库**:全国 191 条著名徒步路线(其中 97 条已接入行程规划,占 51%),按省份分组浏览,五星难度评级,难度/类型/状态/标记筛选与搜索;「想去/走过」标记随手记;手改 `trails.json` 后点「重载线路库」即生效。接入规划的线路可一键跳到规划页预选。
- **智能推荐**:填人均预算、出发站,点几个想看的景色,可限定省份,**可设难度上限(★1–★4,默认「不限」;接了 RunOS 会按当前体能自动收窄)**;从全库确定性打分排序;禁入/关闭的线路一律不推,管控线路带警示,走过的自动排除。填了出发站时人均估算含往返火车实价(12306,去程价×2,会话内按枢纽缓存;无直达车时自动按距离试常见枢纽中转、两段实价相加),预算内/超预算也按含交通口径判;每条结果给出人均花费明细(住宿/餐饮/门票/火车),可一键跳规划页。
- **入门速览**:每条线路卡片直接给日均里程、日均爬升、最高海拔、最长无补给天数(由全程总量折算,每项带数字来源),不用自己拿 100km÷7 天去估;行前装备清单按线路字段确定性推导,卡片即可预览。
- **路线库花费参考**:每条线路卡片给「人均落地约 ¥x」明细(住宿+餐饮+门票,口径与规划页一致);填过出发站的,展开卡片自动补估往返火车,不再只看门票轻敌。
- **身体状态联动**:与同机的 RunOS(运动数据平台)联动,按近期身体状态给每条路线标「适合/有挑战/超现阶段」;不装/不启动 RunOS 也不影响其他功能。
- **行程档案**:每次生成自动存档,随时回看/删除,打开即回填规划要素;旧档天气一键刷新为最新预报(失败则明示快照日期)。

## 技术形态

- Electron + 纯 JS(无框架无构建器),主进程管数据与外部 API,渲染进程用高德 JS API 画图。
- 数据全部是 `data/` 下的 JSON,直接用编辑器就能改线路库。
- LLM 刻意不参与拼装(确定性逻辑),以后做攻略字段抽取时再接 llama-server。

## 使用前必须做

1. `npm install`
2. 到 [lbs.amap.com](https://lbs.amap.com) 注册个人开发者,创建应用,添加两个 Key:
   - **Web服务** → 填入 `data/config.json` 的 `amapKeyWeb`(首次运行会自动从 example 复制)
   - **Web端(JS API)** → 填入 `amapKeyJs`
3. 按你的车改 `data/config.json` 的 `fuel`(百公里油耗、油价);住宿/餐饮估算口径在 `lodging`/`food`。

## 数据维护

```bash
node scripts/backfill-region.mjs            # 报告:哪些线路可补 regionId/node(不改文件)
node scripts/backfill-region.mjs --apply    # 写回 data/trails.json
node scripts/add-regions.mjs                # 新增环线区域定义(幂等:已存在的 id 不覆盖,只补新的)
node scripts/add-lowseason-trails.mjs      # 新增淡季入门线路(幂等:已存在的 id 不覆盖)
```

线路接入行程规划需要 `regionId`(17 个环线区域之一)+ `node`(该区域环线上的节点)。
脚本用球面距离判定「线路起点离哪个环线节点最近」,默认阈值 80km(自驾一天舒适半径),
超出就保持未接入而不是硬塞——归错区域会生成一条根本开不过去的行程,比不接入更糟。
已标注的线路会被校验而不是覆盖:人工标注与地理判定冲突时脚本拒绝写回。

判据只有一条:**就近**。曾试过「同省优先」,被两条真实数据否掉——清凉峰南山脊的
`area` 写明「杭州·临安—安徽绩溪」,本来就走绩溪一侧山脊(距绩溪 10km、距临安 85km),
强制同省会把它推去更远的地方,判据反而制造「开过去更远」的行程。环线跨市界、跨省界
是合法的(南太行/河南收山西的王莽岭,距该环线 14km)。

两类线路脚本会主动拒绝接入,即使距离够近:

- **跨境(港澳台)**:内地车不能自驾跨境进香港/澳门。内地车进港需「粤港跨境私家车
  常规配额」(抽签,中签率极低),反向的「港车北上」只限持香港居民身份证+回乡证的
  香港居民,且每年在内地累计停留不超 180 天;澳门同理需澳车北上/跨境配额。
  麦理浩径/凤凰径/卫奕信径/港岛径/路环岛地理上贴着深圳(直线仅 29-69km),
  haversine 判不出「过不去」,故按省名硬排除——否则会生成「看着合理、根本开不过去」
  的行程。这些线路在库页可查详情,但不能进规划。
- **跨省**:同省没有更近区域时,跨省候选需人工裁决,脚本不自动写。

阈值可调(`--max-km 120`),但放宽后必须人工复核每一条——80km 之外实测已出现错配
(峨眉山后山穿越在乐山,离川西环线 113km)。

## 环线区域的取舍(15 → 17)

原有 9 个区域(川西/滇西北/伊犁/甘南/青海湖·祁连/秦岭/晋北/南太行/京西太行)全是西部与
华北高原。本轮按「悬空线路的地理聚类」新增 6 个,新增顺序即优先级顺序:

| 区域 | 省份 | 接入线路 | 为什么是它 |
|---|---|---|---|
| `huanan` 华南大环线 | 广东 | 7 | 悬空线路最大的一簇(粤港澳 13 条)。12/13 是 ★1-2、`bestMonths` 含冬季,离城近、当季不挤,最匹配入门定位 |
| `zhennan` 浙南雁荡环线 | 浙江 | 4 | 次大簇,4 条全是 ★2、1-2 天、全年可走 |
| `zhexi` 浙西天目环线 | 浙江 | 3 | 徽杭古道/天目山一带的浙西山区。曾为接千八线加龙泉节点,实测环线涨到约 1050km/3 驾车日,5 天就报"偏紧";去掉龙泉后降到约 151km/1 驾车日 |
| `wannan` 皖南徽杭环线 | 安徽 | 4 | 徽杭古道、吴越古道起点在安徽绩溪/宁国,按省拆成两个区域而不是硬凑一个跨省环线 |
| `sanxia` 三峡·清江环线 | 湖北 | 3 | 长江三峡沿线,可与重庆方向线路组合 |
| `zangdongnan` 藏东南·林芝环线 | 西藏 | 4 | 拉萨—米林—派镇—墨脱—波密—然乌一线 |

**两个反直觉的结论,都是被数据否掉的:**

1. **藏东南只能覆盖全藏的一小角。** 西藏 10 条线路散在阿里、日喀则、山南、林芝、
   那曲、昌都、拉萨,横跨 2000km+,做不出一条环线。本区域只覆盖林芝—墨脱—波密—然乌;
   冈仁波齐(阿里)、珠峰东坡(日喀则)、希夏邦马(吉隆)、库拉岗日(山南)、他念他翁(昌都)、
   萨普(那曲)保持未接入。硬凑只会生成「从拉萨开去珠峰大本营」的荒诞行程。

2. **甘南、秦岭不需要新建——它们早就存在。** 上轮讨论时把它们当成「新区域」,
   实际数据里 `gannan`/`qinling` 已在库中,只是线路数偏少(各 2/6 条)。

**环线节点的里程是估算的。** `config.json` 的 `amapKeyWeb` 为空时无法调高德验证,
节点间距按 haversine × 1.30(山区经验放大系数)估算,只保证「不低估」。填好高德 Key 后,
规划器会用真实驾车路线覆盖这些估算值,预算与地图画线都以运行时的高德返回为准。

**单条路段本身就超一整天的情况存在,算法解决不了。** `然乌→拉萨` 一条路约 711km/15.8h,
`planner.js` 只能保证「不让它和前面的短路段堆在同一天」(这一点本轮已修,见下),
但没法把一条路拆成两天。遇到这种区域要么加天数,要么看 `当日驾车超过单日上限,行程偏紧`
的提示。实测最差单日仍超 400km 的区域:`zangdongnan`(711km)、`chuanxi`(623km)、
`sanxia`(524km)、`gannan`(491km)、`qinghaihu`(413km)、`jinbei`(407km)——
这是环线本身太长,不是算法能悄悄消化的,必须让用户看见。

**新增节点会改变已有行程。** `planner.js` 按 `maxDriveKmPerDay`(默认 400km)把环线切成
驾车日,在环线上加节点会增加总里程,可能让该区域已接入线路的行程多出一天车程。
本轮 6 个区域全是新建,不改动原有 9 个环线的节点。

## 冬季线路覆盖的诚实边界

现有 191 条线路中,41 条 `bestMonths` 含 12/1/2 月。接入情况:

| 状态 | 数量 | 说明 |
|---|---|---|
| 已接入 | 14 | 冬季线路的 34%(本轮前 10,本轮 +4) |
| 仍悬空 | 27 | 见下方分类 |

本轮 +4 是:佘山九峰、军嶂古道(新区域 `yangtzedelta`),轿子雪山、雪岭火峰(新区域 `dianzhong`)。

**本轮补建的两个冬季区域**(区域 15 → 17):

| 区域 | 省份 | 接入 | 环线 | 为什么是它 |
|---|---|---|---|---|
| `yangtzedelta` 长三角·太湖环线 | 江苏 | 2 | 336km / 1 驾车日 | 佘山九峰(★1)、军嶂古道(★2)都是库内明确标注 10-12 月的线路,原距最近环线 133km/110km 长期悬空;新建后分别距松江 0km、无锡 9km |
| `dianzhong` 滇中·禄劝东川环线 | 云南 | 2 | 396km / 1 驾车日 | 轿子雪山(4223m)、雪岭火峰(4344m)互相只隔 16km,但距滇西北环线有 119km/105km。这是库里少数「高海拔 + 冬季」兼具的线 |

**顺手修掉一个过严规则。** 回填脚本原先把「跨省」无条件硬排除,导致佘山九峰(上海→江苏 8km)、
三峡之巅(重庆→湖北 8km)、清凉峰(浙江→安徽 10km)、阴条岭(重庆→湖北 54km)全被误卡成悬空。
但环线跨省界本就是常态(南太行/河南收山西王莽岭 14km)。改为与既有测试对齐的判据:
**近距(≤80km)跨省合法,只有「超距 + 跨省」才需人工裁决**。这 4 条现已接入,连带
wannan 4→5、sanxia 3→5。

**东北与新疆:库里根本没有冬季线路,不是「没建区域」。** 全库 41 条冬季线路里,东北只有 2 条
(黑龙江雪乡穿越、吉林老里克湖),新疆 **0 条**。东北那2 条距最近环线节点(北京)1070km 以上,
靠加节点救不了——要真覆盖得先补线路数据,再谈建区域。别在 README 里许诺库里没有的东西。

**华南三条冬季线(船底顶/丹霞山巴寨/天露山)刻意不接,理由是代价大于收益。**
量化后:扩 `huanan` 环线加「英德+韶关」会让它从 661km/2 驾车日涨到 1050km/3 驾车日,
再加天露山则到 1390km/4 驾车日(单条韶关→天露山 leg 就 377km)。代价是**已接入的 7 条线路
全部多出 1 个驾车日**——用户原本 5-7 天的行程被迫加长一天,为了 3 条线赔上 7 条的体验。
为 3 条线另建一个区域又不划算(它们互相 91-232km,不成环)。保持悬空是当前最优解。

**港澳 5 条冬季线路**(麦理浩径/港岛径/凤凰径/卫奕信径/路环岛)因跨境限制也无法接入:
内地车进香港需粤港跨境配额或符合资格的港车北上,澳门同理。这是硬约束,不是数据缺失。

## 数据文件

| 文件 | 作用 |
|---|---|
| `data/config.json` | 高德 Key、油耗与油种、单日驾车上限、机票跳转出发城市(`flightCityPinyin`)、住宿/餐饮估算口径(`lodging`/`food`)、RunOS 服务地址(`runos.baseUrl`) |
| `data/regions.json` | 区域库:枢纽(含 `flightCity` 机票跳转目的地拼音)、所属省份与 `stay` 住宿/餐饮区域基准(驱动分省油价与吃住估算)、自驾环线节点(经纬度)、最佳季节、路况提示 |
| `data/trails.json` | 全国徒步路线库:191 条著名路线按省份编排,含天数/里程/爬升/最高海拔/五星难度评级/通行状态;`scenery` 景色标签(词表见 `lib/recommend.js`,可为空)驱动智能推荐;带 `regionId`+`node` 的条目接入行程规划;`bestMonths` 结构化最佳月份驱动错季提醒与自动选线;`tickets`/`risks`/`supplies` 为自用参考的门票/风险/补给信息(见标注口径);`coordinateNote` 记录坐标修正的来源与依据(改过坐标的条目才有);`sourceNote` 记录里程/爬升/门票等数值的公开资料来源与估算部分(本轮新增的线路才有) |
| `data/stations.json` | 12306 站名↔电报码缓存(自动生成) |
| `data/oilprice.json` | 当日分省油价缓存(自动生成,一天最多打一次站点) |
| `data/trips/` | 每次生成的行程存档(含查询原始数据与行前装备清单),「行程档案」页可回看/删除 |
| `data/marks.json` | 想去/走过标记(路线库卡片上点按钮生成,已走日期可作推荐排除依据) |

**难度评级口径**(五星制):`grade` 人工按社区共识标注,`lib/grading.js` 用日均里程/爬升、最高海拔、技术地形、多日重装算出建议级做交叉校验,单测保证两者相差不超一级,详情页展示分项依据。★1 休闲(景区栈道/城市拉练)→ ★2 入门 → ★3 进阶 → ★4 高难(高海拔/多日重装)→ ★5 极限(顶级长线/技术地形)。`status` 如实标注现实通行状况(鳌太=禁入、年保玉则=关闭),别踩。坐标为近似值,画图/定位够用。

**智能推荐口径**:打分是确定性纯函数(`lib/recommend.js`),景色命中为主(70)、预算余裕为辅(30),同分看花费/天数/名称。**难度不进打分公式,只做硬闸门**(`gradeMin`/`gradeMax`)——入门者看到「★5 排第 8 位」会困惑,「★5 根本不出现」才清晰;门槛不该参与竞争。只在推荐页显式选了难度档、或 RunOS 联动算出体能上限(`fitness.ableGrade`)时才收窄,取不到就不设限(宁缺毋编)。`scenery` 标签从路线自身文本提取 + 人工共识标注(与 grade 同纪律),确实无标志景观的技术线留空——这类线路只在纯预算排序里出现。落地花费估算 = 已知门票(未标注按 0 并**在卡片标「门票未标注」**,不静默低估)+ 两人一间均摊房费 + 餐标按人头(区域有 `stay` 基准则字段级覆盖 config 全局口径),口径与规划页住宿/餐饮一致;**一日线住宿按 1 晚计**(人在景区附近过夜是实花,算 0 晚会让入门者最常选的当日线系统性低估);重装马帮、观光车不计。填了出发站时走**两段式**:先按落地估粗排取 30 条候选池,富化往返火车实价(`rail12306.estimateRoundTrip`:取 10 天后任一天查去程、按规划同口径选座、去程价×2,会话内按枢纽缓存,3 路小并发;无直达车时按距离试最近的中转枢纽、两段实价相加并标注「经 X 中转」),再把预算分按含交通口径重打、截取 12 条——预算内/超预算标记同口径;生成分项实价仍以行程规划为准。路线库卡片展开时用同一缓存按需补估往返火车,查询失败给显式重试(与「确认无直达」分开)。

**入门速览口径**(`lib/quickfacts.js`):把 `trails.json` 的全程总量折算成日均口径,回答「一天走多少公里、爬多少米、最长多久没补给」。日均里程 >15km 或日均爬升 >800m 标黄提醒;最高海拔 ≥4000m 独立提醒(高反不看体力,里程短也不豁免);最长无补给优先看 `supplies` 原文点名,判不了就写「未标注」——**不给编出来的数字**。与 `lib/grading.js` 的评级分项是两套口径:后者面向评级与筛选(权重标定过,单测做交叉校验),这里面向出发前的心理预期,**不要合并**。

**油价口径**:自驾油费优先当日分省实价(`lib/oilprice.js`,解析金投网公开油价页,按 `regions.json` 的 `province` 字段取枢纽省,config 的 `fuel.gasType` 选油种,默认 92#),当日落盘缓存、一天最多打一次站点;取不到实价(区域没标省份/站点改版/网络失败)自动回退 config 的 `pricePerL`,首个驾车日的预算备注言明当前用的是哪种口径。金投油价本身注明"仅供参考,以加油站报价为准"。

**住宿/餐饮区域基准与实花校准**:`regions.json` 可按区域加 `"stay": { "perRoomPerNight", "perPersonPerDay" }`(字段级覆盖 config 全局口径,山区县城和省会不该一个价;现有三条是粗标,按你自己的经验改,不确认就删字段回落全局)。行程走完后在「行程档案」点「记实花」,实际花费进存档并在列表展示——估算准不准,靠真实数据慢慢校准。

**机票兜底**:12306 没有可购车次(无直达/超预售期)时,预算区给「查机票」按钮,跳携程机票列表(出发城市取 config `flightCityPinyin`,目的地取区域库 `hub.flightCity`,日期即行程当日)。只跳转不查价——OTA 价格接口加密,README 既有决策不变。

**行程拼装口径**:车次首选坐席按历时定——10 小时以上优先硬卧/动卧/软卧(夜车硬座不是给预算用的),以下以二等座为主,候选车次展示与预算同口径;预算里火车票与门票按人头乘人数,自驾油费过路按整车、住宿按房间数、餐饮按人头,人均 = 合计 ÷ 人数(整车项均摊)。出发站与区域枢纽相同会直接报错(同站车次无意义)。去程 15 点后才到枢纽、回程 10 点前就发车,相应首末日会挂衔接警告。徒步日撞上坏天气时,若行程有余量,会自动在徒步前插「休整日」把徒步块挪进更好的天气窗口(纯本地预报计算,零新增请求),没有余量则给出 ±3 天整体改期的确定性建议。山顶体感气温按预报点海拔到最高海拔 6.5℃/km 递减折算;Open-Meteo 的网格海拔在山地处可能严重失真,此时折算自动关闭,宁可不显示。行前装备清单(`lib/gear.js`)由线路字段与徒步日天气确定性推导,每条都引用触发原因,不做无依据的通用罗列。

**收藏与足迹口径**:「想去/走过」记在 `data/marks.json`,走过需填日期;推荐一律排除走过的(看新线),路线库可按标记筛选。标记是本地数据,换机不跟随。

**标注口径(自用)**:本应用是单人自用软件,数据标注不必等"社区共识",按公开资料与个人经验整理即可,但两条底线不变——数字与事实不编造,把握不足就留空。`tickets`(参考门票,含常见区间车/管理费)、`risks`、`supplies` 可用 `node scripts/enrich-labels.mjs` 幂等回填(已有值绝不动,管控/禁入线路不自动填票),批量标注后出发前自行核实现价与通行状况;`bestMonths` 可用 `node scripts/enrich-best-months.mjs` 从 bestSeason 原文确定性解析回填(手标为准)。缺标清单:`node scripts/label-backlog.mjs`。

**身体状态联动口径**:启动本机 RunOS 后(地址默认 `http://127.0.0.1:8000`,`config.json` 的 `runos.baseUrl` 可改),路线库顶部出现身体状态条(训练状态标签/准备度/耐力·爬坡得分/今日建议档位/数据同步日期),每条路线的卡片带「适合/有挑战/超现阶段」体能徽章和一句可解释理由,规划页选中线路与行程页徒步日同步提示。匹配是确定性纯函数(`lib/fitness.js`):耐力/爬坡得分锚定当前能驾驭的难度上限(封顶 ★4,极限线不给自动放行),负荷过高/训练中断/准备度低迷自动降档,高反提示独立于体能(耐力再好,海拔线照样提醒)。自动选线也吃这个上限:超上限的线路在自动挑选时靠后。数据缺什么就标 unknown,宁缺毋编。

## 已知边界(自用纪律)

- 12306 只读、不登录、低频 + 10 分钟缓存。**票价来自余票响应内嵌的价格编码字段**(第 39 字段,座位代码+4位价格+5位标记,已用 G/D/K 车实证),不再调用会对非浏览器请求返回 405 的 queryTicketPrice 接口。候选车次切换是同一次查询内的本地操作,不发新请求;切换后存档同步更新。无票时的「邻日参考」是显式点击才发的单次查询,不自动轮询;要把改期算进预算,仍需回表单重新生成。推荐页/路线库的往返火车估算也守同一纪律:每个「出发站→枢纽」会话内只查一次直达,直达没车才按距离试最多 4 个中转枢纽(每枢纽 2 段查询),展开卡片才查、失败不缓存可重试。
- 出发日期超出 16 天预报窗口时,行程后段没有天气数据,天气条会明示而不是静默空白;超出 12306 预售期(约 15 天)会提示"临近出发再查"而不是"没有车次"。规划条件存在 localStorage,换机或清浏览器数据后需重填。
- RunOS 联动是纯只读 GET + 10 分钟缓存:不触发它的同步、不写它的库、不拉起它的进程;同步滞后超 3 天会在状态条明示,数据是否新鲜以 RunOS 里 `last_sync_at` 为准。
- 界面默认走 GPU 合成(滚动/动画流畅);在无头服务或远程桌面(RDP)会话里自动退回软件渲染——那类环境下启动才可靠。需要手动强制软渲染时设环境变量 `GUSHAN_SOFTWARE_RENDER=1`。
- 住宿/餐饮是 `config.json` 口径下的估算(预算备注里言明口径);火车票价/油费/过路费仍全部来自查询原值。
- 高德免费额度自用绰绰有余;路线规划结果会随版本微调,属正常。
- 机票价格不做(OTA 加密数据),以后用"预估 + 跳转"兜底。
- 打包后的 exe 在 `dist/Gushan-portable.exe`;重装系统或换机后先 `npm install && npm run dist`,再以管理员外的普通权限运行 `scripts/make-shortcut.ps1`(带 BOM,勿用无 BOM 编辑器重存)重建桌面快捷方式。
