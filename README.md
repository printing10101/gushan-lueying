# 孤山掠影

自驾×徒步混合行程规划桌面应用(自用)。

> **关于这份仓库**:个人自用工具,顺手开源,按 MIT 发布(见 `LICENSE`)。
> 它依赖你自己的高德/腾讯地图 Key 才能拿到真实驾车路线 —— 不配也能跑,会退回直线估算并把口径写在页面上。
> 行程存档、API Key、站点表等运行时数据都在 `.gitignore` 里,不随仓库分发。
> **线路库的里程、门票、通行状态会随时间变化**(景区会调价、线路会封),出发前请自行核实;
> 山区行程的错误成本是安全级的,本工具的输出不构成安全保证。

**一句话**:选区域(川西、滇西北等 29 个环线区域)+ 出发站 + 日期 + 天数 + 人数 → 一屏得到:往返火车实时票价(12306,支持在同次查询的候选车次间一键切换,夜车自动优先卧铺)、逐日自驾里程/油费/过路费(高德,地图按真实驾车路线画线,油费优先当日分省实价)、徒步日安排(私有线路库,标注当日天气宜否、错季提醒,天气差时有确定性改期/休整建议)、16 天天气窗口,以及含住宿/餐饮估算的预算表(合计+人均,火车票/门票按人头计)。行程自带行前装备清单(由线路字段与天气推导),可导出 Markdown 或打印带走。所有价格可溯源(存档在 `data/trips/`),缺失响亮报错,绝不编造。

- **行程规划**:生成行程、换车次(零新请求)、看徒步日天气与区域路况提示;去程太晚到/回程太早发会挂出衔接警告;无票时可显式点击查邻日车次参考。徒步块排在**能开走的最早一天**(起点即枢纽的入门线落地当天就开走,不再先绕完一圈才开爬);天数放不下该区域任何线路时直接说清「最短的一条要走 N 天、至少给 N+2 天」,不再静默生成一张零徒步日的行程;没配高德 Key 时全程用直线估算并把口径写在页面上。
- **多线串联**:规划页有第二个「顺路再加一条」下拉,选中的线路**各自插在自己的环线节点位置**(同节点的两条线连着走),门票与装备清单按条合并,几天几条线一起扣;选多了放不下会响亮报错而不是硬塞。**余量天数补成「机动/备用日」**(给天气、路况、体力留缓冲),不再挂一句「天数不完全对齐」。
- **逐日天气按当天所在位置**:驾车日锚在当天最后一个节点、徒步日锚在徒步节点,一次多点请求取回(不再是一个锚点覆盖整趟);取不到就退回单点并明说是哪个点的预报。
- **路线库**:全国 191 条著名徒步路线(其中 132 条已接入行程规划,占 69%),按省份分组浏览,五星难度评级,难度/类型/状态/标记筛选与搜索;「想去/走过」标记随手记;手改 `trails.json` 后点「重载线路库」即生效。接入规划的线路可一键跳到规划页预选。
- **智能推荐**:填人均预算、出发站,**出发日期 / 出行人数 / 住宿档次**,点几个想看的景色,可限定省份,**可设难度上限(★1–★4,默认「不限」;接了 RunOS 会按当前体能自动收窄)**;从全库确定性打分排序;禁入/关闭的线路一律不推,管控线路带警示,走过的自动排除。日期/人数/档次不是装饰:它们直接进落地估算(季节系数、房间数、住宿倍数),同一条线换个日期数字就会变。填了出发站时人均估算含往返火车实价(12306,去程价×2,会话内按枢纽缓存;无直达车时自动按距离试常见枢纽中转、两段实价相加),预算内/超预算也按含交通口径判;每条结果给出人均花费明细(住宿/餐饮/门票/火车,缺的显式写「未含」而不是按 0 混进合计),可一键跳规划页。
- **入门速览**:每条线路卡片直接给日均里程、日均爬升、最高海拔、最长无补给天数(由全程总量折算,每项带数字来源),不用自己拿 100km÷7 天去估;行前装备清单按线路字段确定性推导,卡片即可预览。
- **路线库花费参考**:每条线路卡片给「人均落地约 ¥x」+ 分项(住宿/餐饮/门票逐项列,没标的写「未含」),口径与规划页同一份 `lib/budget.js`;卡片上还看得见这个数被哪一档季节系数与哪个档次乘过。填过出发站的,展开卡片自动补估往返火车,不再只看门票轻敌。
- **身体状态联动**:与同机的 RunOS(运动数据平台)联动,按近期身体状态给每条路线标「适合/有挑战/超现阶段」;不装/不启动 RunOS 也不影响其他功能。
- **行程档案**:每次生成自动存档,随时回看/删除,打开即回填规划要素;旧档天气一键刷新为最新预报(失败则明示快照日期)。
- **出发前"离线包"一键产出**:行程页多一个「导出离线包」按钮,选一个位置后自动新建
  `日期-区域-离线包/` 目录,一次写出四个文件——`行程.md`(逐日安排/预算/天气/日照窗口)、
  `驾车轨迹.gpx`(导进两步路或手表)、`行前清单.md`(装备带触发原因 + 一次性开销 + 补给/风险/报备,
  可打印打勾)、`存档.json`(生成时的原始数据副本)。内容由 `lib/pack.js` 的纯函数生成,
  与界面上那几个导出按钮共用同一套实现;写入是**逐文件报告**的,少写一个会直接说出来而不是报成功。
  实测(真实存档):四个文件 2.4KB / 20.5KB / 0.6KB / 21KB,轨迹回读 480 个点、261.6km,
  清单里不含任何金额(金额只在行程.md 的预算表里,口径单列)。
- **离线带走**:行程可导出 **GPX**(驾车段用高德真实 polyline 逐点写出;没配 Key 时用环线节点连直线骨架,并在文件 `metadata` 与每条轨迹的 `desc` 里明说"非真实路线、仅作方向参考")。徒步段应用内没有轨迹数据,只给线路起点路点——**不编一条"看起来像"的徒步轨迹**。反过来也能把两步路/六只脚/Strava 的 GPX 导进来:卡片「导入 GPX」量出里程/爬升/最高海拔与标称值对比,差 ≤10% 才写 `trails.json`,超阈值的一律不写、要人判(命令行等价入口 `scripts/import-gpx.mjs`)。
- **实走回灌**:卡片「记实走」把实走天数/里程/爬升记进 `marks.json`,与线路库标称值并列显示差值,超 15% 标「差得多,待复核」;行程档案「记实花」记真实总花费。估算准不准,靠这些数慢慢校准。

## 技术形态

- Electron + 纯 JS(无框架无构建器),主进程管数据与外部 API,渲染进程用高德 JS API 画图。
- 数据全部是 `data/` 下的 JSON,直接用编辑器就能改线路库。
- LLM 刻意不参与拼装(确定性逻辑),以后做攻略字段抽取时再接 llama-server。

## 使用前必须做

1. `npm install`
2. **路线来源二选一**(都留空也能用,只是里程走直线估算):
   - **腾讯位置服务(推荐先试这家,已实测可用)**:到 [lbs.qq.com](https://lbs.qq.com) 注册 → 控制台创建应用 → 添加 Key,
     服务平台选 **WebServiceAPI** → 填进 `data/config.json` 的 `tencentKeyWeb`。官网 FAQ 原文:
     「注册之后将获得"个人开发者"额度」,且「企业或其他非公益组织使用本服务不享受免费服务」——
     即个人非商业自用有免费额度(具体数值在控制台「配额管理」页看)。
     WebService 这一路**不需要 referer 白名单、不需要签名**(实测:填进 `tencentKeyWeb` 后直接 status=0 可用)。
     注意**腾讯的 JS API 明确"不再支持 file:// 方式"**(官方文档原文),而本应用是 file:// 加载的,
     所以**地图暂时只能用高德底图,腾讯只用来取真实里程/时长/过路费**。
   - **高德**:到 [lbs.amap.com](https://lbs.amap.com) 注册个人开发者 → 控制台「应用管理 → 我的应用 → 创建新应用」→
   在该应用下「添加 Key」,**同一个应用加两个 Key(服务平台选不同)**:
   - 服务平台选 **Web服务** → 填进 `data/config.json` 的 `amapKeyWeb`(路径规划,只需 Key)
   - 服务平台选 **Web端(JS API)** → 填进 `amapKeyJs`;**2021-12-02 之后申请的 Key 还必须把同页面给出的
     「安全密钥」填进 `amapSecurityJsCode`**,否则地图能加载、服务调用却报 `INVALID_USER_SCODE`
     (报错发生在高德内部,页面上只表现为地图空白,极难自查)。
     三个字段(Key、JS API Key、安全密钥)都在 `data/config.json`(首次运行自动从 example 复制;该文件不入库)。
     高德把「基础服务」挂到**技术服务使用许可**下面(许可协议原文:未付款无法获得许可、进而无法使用基础服务),
     个人非商用要走"评估申请";腾讯是注册即给个人额度——这条路更顺,所以先试腾讯。
   - `routeProvider` 留空 = 自动(有高德 Key 用高德、否则有腾讯 Key 用腾讯、都没有就直线估算);
     显式写 `amap`/`tencent`/`estimate` 则以你写的为准,**指定了却没填对应 Key 会直接报错**,
     不会静默退回估算(那会让人以为配好了、其实预算全是估的)。
3. 按你的车改 `data/config.json` 的 `fuel`(百公里油耗、油价、油种);住宿/餐饮估算口径在 `lodging`/`food`,
   季节系数表在 `data/seasonality.json`(节假日安排逐年维护,缺哪年就只按月份算)。
4. 配好 Key 后跑 `node scripts/verify-routes.mjs` 看"直线估算 vs 真实驾车里程"的差距表。

node scripts/add-regions.mjs                # 新增环线区域定义 第1批(幂等:已存在的 id 不覆盖,只补新的)
node scripts/add-regions-2.mjs             # 新增环线区域定义 第2批(18 → 23:桂北/黔东南·黔南/赣西·罗霄/雪乡·镜泊湖/长白山西坡)

node scripts/measure-drive-packing.mjs      # 报告:29 个区域在单日驾车上限下的实际打包结果
                                            # (README「最差单日 XXXkm」这组数字的唯一来源;可加 --max/--only)
node scripts/import-gpx.mjs 轨迹.gpx --trail wusun           # 试运行:实测量 vs 标称值对比表

node scripts/label-backlog.mjs              # 标注欠账:缺 tickets/risks/supplies/bestMonths/regionId/riskNotes/permit

线路接入行程规划需要 `regionId`(29 个环线区域之一)+ `node`(该区域环线上的节点)。
脚本用球面距离判定「线路起点离哪个环线节点最近」,默认阈值 80km(自驾一天舒适半径),
超出就保持未接入而不是硬塞——归错区域会生成一条根本开不过去的行程,比不接入更糟。
已标注的线路会被校验而不是覆盖:人工标注与地理判定冲突时脚本拒绝写回。

判据只有一条:**就近**。曾试过「同省优先」,被两条真实数据否掉——清凉峰南山脊的
`area` 写明「杭州·临安—安徽绩溪」,本来就走绩溪一侧山脊(距绩溪 10km、距临安 85km),
强制同省会把它推去更远的地方,判据反而制造「开过去更远」的行程。环线跨市界、跨省界
是合法的(南太行/河南收山西的王莽岭,距该环线 14km)。

两类线路脚本会主动拒绝接入,即使距离够近:

- **跨境(港澳台)**:内地车不能自驾跨境进香港/澳门。内地车进港需「粤港跨境私家车
  常规配额」(抽签,中签率极低),反向的「港车北上」只限持香港居民身份证+回乡证的
  香港居民,且每年在内地累计停留不超 180 天;澳门同理需澳车北上/跨境配额。
  麦理浩径/凤凰径/卫奕信径/港岛径/路环岛地理上贴着深圳(直线仅 29-69km),
  haversine 判不出「过不去」,故按省名硬排除——否则会生成「看着合理、根本开不过去」
  的行程。这些线路在库页可查详情,但不能进规划。
- **跨省**:近距跨省(≤80km)合法,脚本会照常自动接入——环线跨省界本就是常态(南太行/河南
  收山西王莽岭 14km、皖南/安徽收浙江清凉峰 10km、第 2 批的韭菜岭 69km、八面山 61km、
  元宝山 48km)。只有**超距 + 跨省**才是真错配:那种情况脚本拒绝自动写,需人工裁决。

阈值可调(`--max-km 120`),但放宽后必须人工复核每一条——80km 之外实测已出现错配
(峨眉山后山穿越在乐山,离川西环线 113km)。

## 环线区域的取舍(15 → 17)

原有 9 个区域(川西/滇西北/伊犁/甘南/青海湖·祁连/秦岭/晋北/南太行/京西太行)全是西部与
华北高原。本轮按「悬空线路的地理聚类」新增 6 个,新增顺序即优先级顺序:

| 区域 | 省份 | 接入线路 | 为什么是它 |
|---|---|---|---|
| `huanan` 华南大环线 | 广东 | 7 | 悬空线路最大的一簇(粤港澳 13 条)。12/13 是 ★1-2、`bestMonths` 含冬季,离城近、当季不挤,最匹配入门定位 |
| `zhennan` 浙南雁荡环线 | 浙江 | 4 | 次大簇,4 条全是 ★2、1-2 天、全年可走 |
| `zhexi` 浙西天目环线 | 浙江 | 3 | 徽杭古道/天目山一带的浙西山区。曾为接千八线加龙泉节点,实测环线涨到约 1050km/3 驾车日,5 天就报"偏紧";去掉龙泉后降到约 151km/1 驾车日 |
| `wannan` 皖南徽杭环线 | 安徽 | 4 | 徽杭古道、吴越古道起点在安徽绩溪/宁国,按省拆成两个区域而不是硬凑一个跨省环线 |
| `sanxia` 三峡·清江环线 | 湖北 | 3 | 长江三峡沿线,可与重庆方向线路组合 |
| `zangdongnan` 藏东南·林芝环线 | 西藏 | 4 | 拉萨—米林—派镇—墨脱—波密—然乌一线 |

**两个反直觉的结论,都是被数据否掉的:**

1. **藏东南只能覆盖全藏的一小角。** 西藏 10 条线路散在阿里、日喀则、山南、林芝、
   那曲、昌都、拉萨,横跨 2000km+,做不出一条环线。本区域只覆盖林芝—墨脱—波密—然乌;
   冈仁波齐(阿里)、珠峰东坡(日喀则)、希夏邦马(吉隆)、库拉岗日(山南)、他念他翁(昌都)、
   萨普(那曲)保持未接入。硬凑只会生成「从拉萨开去珠峰大本营」的荒诞行程。

2. **甘南、秦岭不需要新建——它们早就存在。** 上轮讨论时把它们当成「新区域」,
   实际数据里 `gannan`/`qinling` 已在库中,只是线路数偏少(各 2/6 条)。

**环线节点的里程是估算的,但应用能在没 Key 时跑起来。** 配好路线 Key(高德或腾讯)时规划器用真实驾车路线;
一个都没配时,`planner` 自动改用 haversine × 1.30(山区经验放大系数),并在三处把口径说清:页面顶部的橙色提示、逐日表格里每段的「(估算里程)」、
预算备注。导出的 Markdown 与打印件同样带这条说明——**用户看到的每一个公里数都知道自己是估的还是量的**。
过路费此时走 `calcCosts` 既有的 0.45 元/km 估算分支并标「(估)」。
估算系数 `LOOP_FACTOR` / 车速 `AVG_KMH` 收在 `lib/amap.js` 单一来源,
`scripts/verify-routes.mjs` 与 `scripts/smoke-region.mjs` 都引用它,不再各抄一份
(抄本一旦和 planner 用的系数漂移,「估算 vs 真实」差距表就在骗人)。
**"只保证不低估"这句是错的,已按实测删掉。** 2026-10-07 用腾讯真实路网跑完全库 99 条 leg(当时 18 个区域;现 29 个区域共 138 条 leg)后发现:
估算既会低估也会高估——低估侧有 `成都→映秀 93→79km(-15%)`、`无锡→上海 153→137km(-10%)` 等,
高估侧有 `映秀→四姑娘山镇 71→125km(+76%)`、`奔子栏→飞来寺 60→234km(+290%)` 等。
所以估算的正确说法是**量级参考**,不是"保守上限"。真实偏差表用 `node scripts/verify-routes.mjs` 生成。
注意:坏坐标、配额超限、网络失败**不会**被估算兜掉——只有「没配 Key」这一种确定情况才降级,
否则 `regions.json` 填错坐标会静默变成一条像模像样的假里程。

配好 Key 后可以一次跑出全库对比:

```
node scripts/verify-routes.mjs              # 试运行,输出估算 vs 真实的逐条差距表
node scripts/verify-routes.mjs --only yili  # 只查一个区域
```

它会把 29 个区域每条 leg 的估算值与真实值并排列出,并单独标出两类值得警惕的偏差:
**严重低估**(真实比估算少 10% 以上,会让预算偏高)和**严重高估**(真实比估算少 60%
以上,说明这段直线×1.3 明显失准)。目前 `regions.json` 的节点只有 `name/lng/lat`,
没有存真实里程的字段,所以脚本先只出对比表,写回需要另行设计。

**高德调用有会话级缓存。** `lib/amap.js` 按节点坐标缓存 `drivingRoute` 结果,
含 in-flight 去重、失败不缓存(一次限频不会让该路段整个会话永久失败)、反向 leg
独立 key。没有缓存的话,`planner` 每次生成行程都会把整个环线的 leg 重查一遍
(`yili` 7 条、`zangdongnan` 6 条),个人 Key 的 QPS(通常 3)会被打爆、配额也会飞快耗尽。

**单日驾车上限是硬切分依据:能拆开的绝不塞进一天,拆不动的才挂提示。** `planDays` 用
「前瞻切分」——当天已有路段、且加上下一段会超 `maxDriveKmPerDay`(默认 400km)时,先收当天再走下一段。
此前是「加完再判」,实测 `jingxi` 五段 81+77+103+132+122 会整圈塞成**一天 515km** 还标「行程偏紧」:
第 4 段前只累积到 393(未到上限)所以不切,最后一腿又走收尾分支,515 就这么长出来了。
改后 `jingxi` 变成 393 + 122 两天、零超限提示。全库影响面(29 区域 × {5,7,10} 天 = 87 个场景):
超 400km 的驾车日 **24 → 6**,总里程逐区守恒;代价是 `chuanxi`/`gannan`/`jingxi`/`sanxia`
在 7 天档各多出一个驾车日(2→3),短天数行程更容易看到「驾车中段需要 N 天」的偏紧提示——
那是真的更紧了,以前是被超限的一天掩盖住。

**单条路段本身就超一整天的情况存在,算法解决不了。** `然乌→拉萨` 一条路约 711km,
没法把一条路拆成两天,只能让它独占一天并保留 `overKm` 提示。
按 `node scripts/measure-drive-packing.mjs` 实测,最差单日仍超 400km 的**只剩 `zangdongnan`(711km)**
——其余 28 个区域的超限单日全部来自打包策略,已修掉(此前 README 列的 chuanxi 623/sanxia 524/
gannan 491/qinghaihu 413/jinbei 407 都是"能拆却没拆"的假超限)。这是环线本身太长,不是算法能悄悄消化的,
必须让用户看见;要绕开只能加天数或换区域。

**新增节点会改变已有行程。** `planner.js` 按 `maxDriveKmPerDay`(默认 400km)把环线切成
驾车日,在环线上加节点会增加总里程,可能让该区域已接入线路的行程多出一天车程。

滇中·禄劝东川、`jingbei2` 京北·密云长城(详见下方冬季段)。`jingbei2` 的建法与上表
6 个都不同:它的第 0 节点刻意用县城「密云」而非北京市中心,原因见下方专门说明。

### `jingbei2` 为什么环线起点是「密云」而不是「北京」

最初的方案是「北京→鹿皮关→金山岭→黄崖关→北京」(343km),一写入就撞墙:地理校验
「已标注线路的最近环线节点必须属于所挂区域」全线告红,因为 `jingxi` 16 条北京西郊
线路(香八拉 21km、鹫峰环线 31km、云蒙山 72-77km)起点都在「北京」节点 80km 内。

**换枢纽解决不了。** 北京西站/清河/通州/顺义/承德/蓟州/兴隆/怀柔八个候选全试过,
抢走的线路数量只增不减(清河最糟,抢 6 条)——因为抢不抢由**三条长城的节点位置**决定,
与第 0 节点选谁无关。这条思路本身就是错的,不能再往下试。

真正的解法是放弃「第 0 节点=大城市」这个约束,把起点放到京东本地县城「密云」:

| | 北京起点 | 密云起点 |
|---|---|---|
| 环线里程 | 343km | **208km(-39%)** |
| 驾车日 | 2 | **1** |
| 抢 jingxi 线路 | 5-6 条 | **0 条** |

`loop[0]` 的语义是「环线第一站」不是「城市中心」,planner 只用它算 leg 与天气锚点;
现有 29 个区域的 `loop[0]` 已经是成都/映秀/四姑娘山镇这类市镇。三条长城距密云
19/46/55km,全在当天往返舒适半径内。

**代价必须说清**:`hub.railStation` 仍是「北京西」而不是「密云」——密云站虽在 12306
站表里(共 3404 站)但只办普速,当不了高铁枢纽。玩家从北京西站落地后还要自己开
约 90km 到密云,这段**不计入环线里程**。已写进区域 `notes`。

**3 条地理上更近但刻意不换区的线路**:

| 线路 | 原标注 | 距 jingbei2 节点 | 不换区的理由 |
|---|---|---|---|
| 箭扣长城(西栅子—慕田峪) | `jingxi`/北京 73km | 鹿皮关 25km | ★3/2 天/部分管控的野长城,与三条 1 天入门长城性质不同 |
| 云蒙山—天仙瀑 | `jingxi`/北京 72km | 鹿皮关 10km | 山地纵走不是长城 |
| 云蒙山青空岭环线 | `jingxi`/北京 77km | 鹿皮关 4km | 山地纵走不是长城 |

三条挂 `jingxi`/北京 本身成立(72-77km 仍在 80km 阈值内,不是错配),换过去会让
`jingxi` 平白少 3 条可选线路(16→13)而 `jingbei2` 本已有 3 条 0km 的入门长城,
覆盖不增反损。**「距离是必要条件,不是充分条件」**——例外登记在
`backfill-region.mjs` 的 `MANUAL_EXCLUDE` 与测试的 `KEEP_MANUAL`,两处同源必须同步改。
回填报告会把它们单列为「人工维持原标注」,不静默吞掉。

**雾灵山刻意不接**:距金山岭仅 27km 能接,但 ★3/2118m/`status=管控`/`bestMonths` 只 5-9 月。
它是独立山体(京东第一峰)不是长城体系,接进来区域定位变脏,且 10-12 月无路可走——
而补冬季覆盖正是本轮目的。

**顺手修掉一个过严规则。** 回填脚本原先把「跨省」无条件硬排除,导致佘山九峰(上海→江苏 8km)、
三峡之巅(重庆→湖北 8km)、清凉峰(浙江→安徽 10km)、阴条岭(重庆→湖北 54km)全被误卡成悬空。
但环线跨省界本就是常态(南太行/河南收山西王莽岭 14km)。改为与既有测试对齐的判据:
**近距(≤80km)跨省合法,只有「超距 + 跨省」才需人工裁决**。这 4 条现已接入,连带
wannan 4→5、sanxia 3→5。

**东北与新疆:不是「没建区域」,是库里确实没有能接的冬季线路。** 逐条实测过:

- **新疆**:12 条新疆线路里,`bestMonths` 含 12/1/2 月的**只有 0 条**。唯一看着像的
  库姆塔格沙漠穿越(`bestMonths=[3,4,10,11]`)其实不含冬季月,而且它距最近节点
  (伊犁/那拉提)**561km**。其余悬空的 6 条距离是:狼塔C 267km、狼塔V 254km、
  狼塔C+V 267km、博格达 389km、车师古道 470km、喀纳斯大环线 673km。
  试过扩 `yili` 环线加霍城/果子沟/赛里木湖(596→686km,驾车日 2→2 不变,
  代价不高),但**能接上的新线路是 0 条**——伊犁周边库里的 5 条线已全部接入。
  真实存在的新疆冬季线路(赛里木湖蓝冰、伊犁雪原、狼塔冬季穿越)库里都没有,
  要覆盖必须**先补数据再谈建区域**。别在 README 里许诺库里没有的东西。
- **东北:曾判「加节点救不了」——那句判定本身没错,第 2 批改用独立区域绕过了它。**
  「距最近环线节点(北京)1070km 以上」所以把东北的点挂到既有环线上确实无解;但两个小区簇
  各自成立:`xuexiang` 用哈尔滨做枢纽接雪乡(63km)、镜泊湖(49km),`changbaidong` 用延吉
  做枢纽接老里克湖(10km)、长白山西坡(29km),各 2 条线、各 2 个驾车日。东北 2 条冬季线
  (雪乡穿越、老里克湖)**现已全部可规划**,冬季覆盖里「东北 0 区域」这一栏不再成立。

**华南三条冬季线(船底顶/丹霞山巴寨/天露山)刻意不接,理由是代价大于收益。**
量化后:扩 `huanan` 环线加「英德+韶关」会让它从 661km/2 驾车日涨到 1050km/3 驾车日,
再加天露山则到 1390km/4 驾车日(单条韶关→天露山 leg 就 377km)。代价是**已接入的 7 条线路
全部多出 1 个驾车日**——用户原本 5-7 天的行程被迫加长一天,为了 3 条线赔上 7 条的体验。
为 3 条线另建一个区域又不划算(它们互相 91-232km,不成环)。保持悬空是当前最优解。

**港澳 5 条冬季线路**(麦理浩径/港岛径/凤凰径/卫奕信径/路环岛)因跨境限制也无法接入:
内地车进香港需粤港跨境配额或符合资格的港车北上,澳门同理。这是硬约束,不是数据缺失。

**难度评级口径**(五星制):`grade` 人工按社区共识标注,`lib/grading.js` 用日均里程/爬升、最高海拔、技术地形、多日重装算出建议级做交叉校验,单测保证两者相差不超一级,详情页展示分项依据。★1 休闲(景区栈道/城市拉练)→ ★2 入门 → ★3 进阶 → ★4 高难(高海拔/多日重装)→ ★5 极限(顶级长线/技术地形)。`status` 如实标注现实通行状况(鳌太=禁入、年保玉则=关闭),别踩。坐标为近似值,画图/定位够用。

**智能推荐口径**:打分是确定性纯函数(`lib/recommend.js`),景色命中为主(70)、预算余裕为辅(30),同分看花费/天数/名称。**难度不进打分公式,只做硬闸门**(`gradeMin`/`gradeMax`)——入门者看到「★5 排第 8 位」会困惑,「★5 根本不出现」才清晰;门槛不该参与竞争。只在推荐页显式选了难度档、或 RunOS 联动算出体能上限(`fitness.ableGrade`)时才收窄,取不到就不设限(宁缺毋编)。`scenery` 标签从路线自身文本提取 + 人工共识标注(与 grade 同纪律),确实无标志景观的技术线留空——这类线路只在纯预算排序里出现。落地花费由 `lib/budget.js` 计算(口径见上文「落地成本模型口径」):门票未标注 → 该项**不进合计**并挂「门票未标注」角标(旧口径按 0 计,等于假装免费);房费按 `ceil(人数 ÷ 每间人数)` 取整间数(1 人就是整间房,不再 ÷2);餐标按人头(区域有 `stay` 基准则字段级覆盖 config 全局口径);**一日线住宿按 1 晚计**(人在景区附近过夜是实花,算 0 晚会让入门者最常选的当日线系统性低估);出发日期/人数/档次三项都进公式。向导马帮、观光车这类没有实数的项只列示不给金额,`extraFees` 没标就不产出这一条。填了出发站时走**两段式**:先按落地估粗排取 30 条候选池,富化往返火车实价(`rail12306.estimateRoundTrip`:取 10 天后任一天查去程、按规划同口径选座、去程价×2,会话内按枢纽缓存,3 路小并发;无直达车时按距离试最近的中转枢纽、两段实价相加并标注「经 X 中转」),再把预算分按含交通口径重打、截取 12 条——预算内/超预算标记同口径;生成分项实价仍以行程规划为准。路线库卡片展开时用同一缓存按需补估往返火车,查询失败给显式重试(与「确认无直达」分开)。

**入门速览口径**(`lib/quickfacts.js`):把 `trails.json` 的全程总量折算成日均口径,回答「一天走多少公里、爬多少米、最长多久没补给」。日均里程 >15km 或日均爬升 >800m 标黄提醒;最高海拔 ≥4000m 独立提醒(高反不看体力,里程短也不豁免);最长无补给优先看 `supplies` 原文点名,判不了就写「未标注」——**不给编出来的数字**。与 `lib/grading.js` 的评级分项是两套口径:后者面向评级与筛选(权重标定过,单测做交叉校验),这里面向出发前的心理预期,**不要合并**。

**油价口径**:自驾油费优先当日分省实价(`lib/oilprice.js`,解析金投网公开油价页,按 `regions.json` 的 `province` 字段取枢纽省,config 的 `fuel.gasType` 选油种,默认 92#),当日落盘缓存、一天最多打一次站点;取不到实价(区域没标省份/站点改版/网络失败)自动回退 config 的 `pricePerL`,首个驾车日的预算备注言明当前用的是哪种口径。金投油价本身注明"仅供参考,以加油站报价为准"。

**落地成本模型口径**(`lib/budget.js`,设计稿 `docs/superpowers/specs/2026-10-07-落地成本模型-design.md`):
分项模型,推荐页与规划页**共用同一套公式**——以前 `recommend.costBreakdown` 与 `planner.stayBudget`
各写一遍吃住算法,一侧修了「1 天线按 1 晚计」、另一侧还在按 0 晚算(INSTINCTS 记过这个后果),
现在 `nights` 一律由调用点算好传入(`hikeNights` 徒步语义 / `tripNights` 行程语义),差异写在眼前。

- **人均 = 合计 ÷ 人数,房间数向上取整**:一个人也要包整间房。旧公式硬写 `房费 ÷ 2`,等于永远假设两人同行,
  所以一条 1 天无门票线从 **¥180** 变成 **¥280**——这是修 bug(推荐页在错、planner 在对),不是回归。
- **三个输入真的进公式**:出发日期(季节系数)、出行人数(房间数)、住宿档次(经济 ×0.6 / 舒适 ×1.0)。
  以前这三样一个都不吃,所以换滤镜调预算数字一动不动。
- **季节系数四路取最大值**:区域专属旺季 > 法定节假日 > 全国月份淡旺 > 中性基准 1.0。
  取最大而不是"命中即返回",因为国庆正落在川西秋色旺季,按优先级会取到区域 1.4 把节假日 1.8 压掉——
  那恰恰是最贵的时候;也不叠乘(1.4×1.8=2.52 没依据)。中性基准不参与取大(否则淡季 0.9 永远被 1.0 压掉)。
  餐饮系数**不跟随住宿**(住宿涨得比吃饭猛),节假日没写 `food` 就按 1.0。
- **未知是一等公民**:门票没标 → 该项 `null`、不进合计、计入 `unknownCount`,卡片挂「门票未标注」并在分项里写「未含」;
  进山费/观光车只有 `extraFees` 真有实数时才产出条目。**绝不写 0 冒充知道,绝不估一个数。**
- 日期留空按中性基准并明说;年份超出节假日表 → 只走月份并注明。
- `data/seasonality.json` 的节假日安排是抄来的,每条都带 `source`;**其中元旦/春节/劳动节的日期我没能二次抓到
  国办通知原文**(政府页抓取失败,领馆口径与国办口径在劳动节上还差一天),文件里已逐条写明待核状态。
  系数本身全是估的,所以卡片必须显示用的是哪一档、哪一路命中。

**住宿/餐饮区域基准与实花校准**:`regions.json` 可按区域加 `"stay": { "perRoomPerNight", "perPersonPerDay" }`(**29 个区域现已全部标了**,但都是粗标,按你自己的经验改,不确认就删字段回落全局)。字段级覆盖是设计允许的——**只写一半时,缺的那半回落 config 全局值**(目前仅 `dianxibei` 只标了餐标 90、没标房费,房费走全局口径;滇西北是成熟旅游区,若你手上有当地实价,补上更准)。行程走完后在「行程档案」点「记实花」,实际花费进存档并在列表展示——估算准不准,靠真实数据慢慢校准。

**住宿档次与两种计价单位(2026-10-08)**:规划页(行程页)与推荐页都有档次下拉——**客栈标间 / 青旅床位 / 酒店**,默认客栈(基准 ×1.0)。关键是这两个档的**计价单位不同,不是同一个价打折**:

| 档 | 计价单位 | 公式 | 人均特征 |
|---|---|---|---|
| 客栈 / 酒店 | **房间** | `晚数 × 房价 × ceil(人数 ÷ 每间人数)` | 随人数阶梯变化(1 人¥260、2 人人均¥130) |
| 青旅 | **床位** | `晚数 × 床位价 × 人数` | **恒等于床位价,与人数无关** |

青旅若按"整间房价 × 0.6"算会让人均随人数跳(实测 1 人 ¥156 / 2 人 ¥78 / 3 人 ¥104),而真实青旅人均本就该是常数。**给区域标床位价即可启用床位口径**:

```json
"stay": {
  "perRoomPerNight": 260, "perPersonPerDay": 90,
  "tiers": { "青旅": { "perBedPerNight": 70 } }   // 床位价,一人一晚一个床位
}
```

`tiers` 也可给**任一档绝对价**(如 `tiers.酒店.perRoomPerNight`),**有绝对价就不再乘档次系数**(否则打两次折)。没标的档回落"基准价 × 系数"(青旅 ×0.6 / 客栈 ×1.0 / 酒店 ×1.8,酒店那档是初始估计、无实测依据),备注会写明用的是哪一种。旧档名 `经济`/`舒适` 自动映射到 青旅/客栈,存档与 localStorage 里的旧值都兼容。

**青旅床位价的数据来源(2026-10-08 抓取)**:`regions.json` 的 `stay.tiers.青旅.perBedPerNight` 抓自 **Hostelworld 城市页**的「在售床位中位价」。URL **必须带 `?currency=CNY`**——不加会按 IP 返回 KHR 等其他币种,靠汇率换算会引入误差。每个数字都带 `source`(来源 + URL + 核对日期 + 样本数),与门票同一套纪律:**数字必须与出处配套**;数据层有断言把关(缺出处、负数、日期格式错、把房价误填进床位价,都会被测试挡下)。

**未标床位价的 19 个区域**(伊犁/甘南/青海湖/晋北/南太行/浙南/三峡/藏东南,第 2 批的桂北/黔东南/赣西/雪乡·镜泊湖/长白山西坡,第 3 批的黔西·乌蒙/赣东北·武夷北麓/滇西·大理/海南·五指山/豫西·伏牛山/黔东北·梵净山)走 `config.json` 的 `lodging.perBedPerNight` 全局兜底(**74**,来自上表城市中位价再取中位、每城等权)。原因是伊宁在 Hostelworld 上没有城市页(404)、大同/拉萨/温州/新乡/宜昌的城市页没有床位数据,第 2、3 批的桂林/凯里/宜春/哈尔滨/延吉/六盘水/上饶/大理/海口/洛阳/铜仁本批都没去抓——**没数据就留空,不编**。这 19 个区域的 `perRoomPerNight`/`perPersonPerDay` 仍是粗标(与另外 10 个同纪律,无出处标注)。

**这个数的口径限制(必须知道)**:① 它是 Hostelworld 的**在售参考价**,随季节与日期波动(旺季可翻倍);② Hostelworld 偏**国际背包客**定位,可能高于美团/携程上的国内青旅;③ 价格取自**枢纽城市**,而行程中段多在县城/景区,当地青旅通常更便宜——所以这个数对"首末日在枢纽城市"较准,中段偏保守。

**机票兜底**:12306 没有可购车次(无直达/超预售期)时,预算区给「查机票」按钮,跳携程机票列表(出发城市取 config `flightCityPinyin`,目的地取区域库 `hub.flightCity`,日期即行程当日)。只跳转不查价——OTA 价格接口加密,README 既有决策不变。

**行程拼装口径**:车次首选坐席按历时定——10 小时以上优先硬卧/动卧/软卧(夜车硬座不是给预算用的),以下以二等座为主,候选车次展示与预算同口径;预算里火车票与门票按人头乘人数,自驾油费过路按整车、住宿按房间数、餐饮按人头,人均 = 合计 ÷ 人数(整车项均摊)。出发站与区域枢纽相同会直接报错(同站车次无意义)。去程 15 点后才到枢纽、回程 10 点前就发车,相应首末日会挂衔接警告。徒步日撞上坏天气时,若行程有余量,会自动在徒步前插「休整日」把徒步块挪进更好的天气窗口(纯本地预报计算,零新增请求),没有余量则给出 ±3 天整体改期的确定性建议。山顶体感气温按预报点海拔到最高海拔 6.5℃/km 递减折算;Open-Meteo 的网格海拔在山地处可能严重失真,此时折算自动关闭,宁可不显示。行前装备清单(`lib/gear.js`)由线路字段与徒步日天气确定性推导,每条都引用触发原因,不做无依据的通用罗列。

**收藏与足迹口径**:「想去/走过」记在 `data/marks.json`,走过需填日期;推荐一律排除走过的(看新线),路线库可按标记筛选。标记是本地数据,换机不跟随。

- **门票口径分三档(2026-10-08 起)**:门票是参考价、会随季节与政策变,而且同一景区不同来源会互相矛盾
  (实测:轿子雪山二手来源写 30 元、攻略写 54 元;牛背山收费结构变动多次)。所以补数据时按来源分档,
  **数字与来源必须配套**:
- **补门票的方法(2026-10-08 起的固定流程)**:① 先用检索找**官方页**(景区官网票务页 / 政府定价公示 /
  景区运营方官网),标题里带数字的最省事;② 官方页若是 **JS 动态渲染**(常见:票价由接口填进去),
  用 `fetch` 只能拿到占位符——**改用浏览器工具打开页面读渲染后的文本**,这条路已实测有效
  (金山岭 ¥65、古马台/古北水镇票制都是从官方票务页/官网渲染后读到的);
  ③ 官方资源不可用时退到 OTA 门票页,并在 `ticketNote` 里注明"非官方公示";
  ④ 只有互相矛盾的攻略数字 → 不填,只记录分歧。
  - **A 档**:景区官网票务页 / 政府定价公示 → 填 `tickets`,附 `ticketSource { source, url, checkedAt }`。
  - **B 档**:权威媒体报道 / 本地政务号 → 可填,但必须在 `ticketNote` 里写清"含什么、不含什么"
    (套票、接驳车、索道单列到 `extraFees`),否则一个数字会系统性低估。
  - **C 档**:只有攻略/OTA 数字 → **不填数字**,只在 `ticketNote` 里记下候选值与分歧原因。
  - 免票也必须**有出处**才填 0。数据层有**反向断言**把关:`tickets: 0` 没有 `ticketSource`
    会被测试挡下(上有"有来源却无数字",这是"无来源硬填 0")。0 会静默进预算合计,
    等于告诉用户"这段不要钱",所以查过但找不到出处时正确做法是**留空**(未标注),
    不是填 0。2026-10-08 实测库里有 59 条 `tickets: 0` 全无出处,已一律改为未标注。
  卡片上会显示「门票参考来源:… (日期 核对) [看原文]」与口径说明;行程预算里"徒步费用"那条备注
  同样带来源与核对日期。数据层有断言把关:`ticketSource` 存在就必须有有效数字,而"只有 `ticketNote`
  没有数字"(查过但不敢填)是**合法的**——那正是我们要的诚实状态。欠账清单:`node scripts/label-backlog.mjs tickets`。

**标注口径(自用)**:本应用是单人自用软件,数据标注不必等"社区共识",按公开资料与个人经验整理即可,但两条底线不变——数字与事实不编造,把握不足就留空。`tickets`(参考门票,含常见区间车/管理费)、`risks`、`supplies` 可用 `node scripts/enrich-labels.mjs` 幂等回填(已有值绝不动,管控/禁入线路不自动填票),批量标注后出发前自行核实现价与通行状况;`bestMonths` 可用 `node scripts/enrich-best-months.mjs` 从 bestSeason 原文确定性解析回填(手标为准)。缺标清单:`node scripts/label-backlog.mjs`。

**身体状态联动口径**:启动本机 RunOS 后(地址默认 `http://127.0.0.1:8000`,`config.json` 的 `runos.baseUrl` 可改),路线库顶部出现身体状态条(训练状态标签/准备度/耐力·爬坡得分/今日建议档位/数据同步日期),每条路线的卡片带「适合/有挑战/超现阶段」体能徽章和一句可解释理由,规划页选中线路与行程页徒步日同步提示。匹配是确定性纯函数(`lib/fitness.js`):耐力/爬坡得分锚定当前能驾驭的难度上限(封顶 ★4,极限线不给自动放行),负荷过高/训练中断/准备度低迷自动降档,高反提示独立于体能(耐力再好,海拔线照样提醒)。自动选线也吃这个上限:超上限的线路在自动挑选时靠后。数据缺什么就标 unknown,宁缺毋编。

## 已知边界(自用纪律)

- 12306 只读、不登录、低频 + 10 分钟缓存。**票价来自余票响应内嵌的价格编码字段**(第 39 字段,座位代码+4位价格+5位标记,已用 G/D/K 车实证),不再调用会对非浏览器请求返回 405 的 queryTicketPrice 接口。候选车次切换是同一次查询内的本地操作,不发新请求;切换后存档同步更新。无票时的「邻日参考」是显式点击才发的单次查询,不自动轮询;要把改期算进预算,仍需回表单重新生成。推荐页/路线库的往返火车估算也守同一纪律:每个「出发站→枢纽」会话内只查一次直达,直达没车才按距离试最多 4 个中转枢纽(每枢纽 2 段查询),展开卡片才查、失败不缓存可重试。
- 出发日期超出 16 天预报窗口时,行程后段没有天气数据,天气条会明示而不是静默空白;超出 12306 预售期(约 15 天)会提示"临近出发再查"而不是"没有车次"。规划条件存在 localStorage,换机或清浏览器数据后需重填。
- RunOS 联动是纯只读 GET + 10 分钟缓存:不触发它的同步、不写它的库、不拉起它的进程;同步滞后超 3 天会在状态条明示,数据是否新鲜以 RunOS 里 `last_sync_at` 为准。
- 界面默认走 GPU 合成(滚动/动画流畅);在无头服务或远程桌面(RDP)会话里自动退回软件渲染——那类环境下启动才可靠。需要手动强制软渲染时设环境变量 `GUSHAN_SOFTWARE_RENDER=1`。
- 住宿/餐饮是 `config.json` 口径下的估算(预算备注里言明口径);火车票价/油费/过路费仍全部来自查询原值。
- 高德免费额度自用绰绰有余;路线规划结果会随版本微调,属正常。
- **路线来源三选一(`lib/routing.js`)**:两家厂商的约定几乎处处相反,所以隔在各自模块里、只对外给一种形状
  (`{distanceKm, durationHours, tolls, path, estimated, provider}`):

  | 维度 | 高德 | 腾讯 | 直线估算(兜底) |
  |---|---|---|---|
  | 坐标顺序 | `lng,lat` | **`lat,lng`**(写反会跑到地球另一边) | 同高德 |
  | 距离单位 | 米 | 米 | 公里 |
  | 时长单位 | 秒 | **分钟** | 按 45km/h 估 |
  | 过路费 | 有 `tolls` | 有 `toll`(元;官方字段表没列它,**实测响应里有**,缺了才回落估算并标「(估)」) | 按 0.45 元/km 估 |
  | 地图(JS API) | 支持(需 Key + 2021-12-02 后的安全密钥) | **官方明确不支持 file://** → 本应用画图仍走高德 | 只画节点直线骨架 |
  | polyline 解码 | 原文格式 | 压缩数组:前两点是度原值、其余按差分累加(1e-6 度/单位),**已用真实响应验证**(夹具 `test/fixtures/tencent-driving-real.json`:514 点解出后球面长度 76.1km vs 接口 76.2km) | — |

  每次生成行程的调用量 = 环线路段数(全市 3~8 次,中位 6 次),会话级缓存去重
  (`lib/route-cache.js`,两家共用:in-flight 去重、失败不缓存、坏坐标不进缓存)。
- **票价的三种"没有价"要分清**:预售期外(过些天再查就有)、接口失败(12306 会连续几分钟返回非 JSON,
  实测过)、确实没有可购车次。前两种现在会填**占位估算**(往返实价 ÷ 2 × 人数,复用推荐页那套),
  页面明写"占位估算,出发前请复核",不再让预算留空洞;连占位价都拿不到时说清原因、金额仍为 null。
- **打包版(Gushan-portable.exe)的数据目录在 exe 旁边**:`dist/data/`。为什么不是随便放:portable 目标
  每次启动都把应用解到 `%TEMP%` 再运行,那里的 `data/` 只是只读种子快照——**用户填的 Key、生成的行程
  会在退出时随临时目录一起消失**(实测过:那个目录里根本没有 config.json)。所以打包运行时会用
  `PORTABLE_EXECUTABLE_DIR/data`,并且首次启动把种子文件(以及开发机 data/ 里的 marks/trips)复制过去。
  重新打包**不会**清掉 `dist/data/`(已验证:构建保留 dist 下的未知文件)。
- **打包版首次运行要填一次 Key**:exe 里**刻意不含** `data/config.json`(`build.files` 里排除了它,防止
  你的 Key 被打进分发包),所以首次启动生成的 `dist/data/config.json` 是空的。把 Key 填进去(或直接
  复制开发目录的 `data/config.json` 过去)即可——之后双击桌面图标就是"真实里程 + 真实过路费 + 地图"的完整体。
- **本地 http 来源(默认自动,`GUSHAN_SERVE` 可覆盖)**:腾讯 GL 拒绝 `file://`,所以配了腾讯地图 Key
  时应用**自动**改用 `http://127.0.0.1:随机端口` 加载页面——不需要任何环境变量,打包后的 exe 同样带地图。
  规则与理由见 `lib/serve-policy.js`(纯函数、有单测):**有高德 JS Key 就不开本地端口**(那条在
  `file://` 下可用且带夜色主题,能少开一个口就少开);**`GUSHAN_SERVE=0` 强制回 `file://`**(逃生开关),
  `GUSHAN_SERVE=1` 强制开。启动日志会打一行 `[来源策略] auto —— …` 说明当前用的是哪种、为什么。
  **暴露面**:本地服务只放行 `src/` 与 `lib/`(地图只需要源码),`data/` 从端口读不到——
  实测 `GET /data/config.json` 与 `/data/trips/` 都是 **403**,并有两条断言盯着(`npm run smoke:serve`)。

- **地图:腾讯 GL 已接通(2026-10-08 实测)**,实现层在 `lib/map-impl.js`(高德/腾讯两套 SDK 藏在它后面,
  `app.js` 不出现任何一家的 API 名)。三条实测结论:**腾讯的 Key 一把通吃**(控制台勾 WebServiceAPI 即可,
  JavaScript API GL 自动可用,**不需要单独建 Key、也不需要白名单**);**腾讯拒绝 `file://`**,
  只能在 `http://127.0.0.1` 来源下用;`GUSHAN_SERVE=1 npm run app` 即以本地 http 启动(默认仍是 file://)。
  CSP 要为 GL 放行四组域(实测逐个抓出来的):`map.qq.com`(SDK)、`mapapi.qq.com`(字形/图标)、
  `*.gtimg.com`(瓦片)、`*.qpic.cn`(样式),以及 **`worker-src 'self' blob:`**——GL 引擎用 blob worker
  解码瓦片,不放开则"canvas 建起来了但一个瓦片都不请求",页面看着像加载失败。
  **已知差异**:腾讯底图是默认矢量样式,没有高德那条 `darkblue` 的夜色主题,观感与界面不完全一致;
  不拿 CSS 滤镜假装一致。
- **地图画真实路线的"来源问题"(spike,默认关闭)**:腾讯 GL 的官方原文是"不再支持 file:// 方式使用
  Javascript API GL",而本应用一直用 `loadFile` 加载,所以那条路要先解决"来源"。做法:加一个
  **只绑回环、随机端口、只读仓库内文件**的本地静态服务,设 `GUSHAN_SERVE=1` 时改用
  `http://127.0.0.1:端口/src/index.html` 加载(默认仍是 file://,行为不变,可回退)。
  实测这条路径可用:窗口正常起来、29 个区域与 191 张卡都在、`contextIsolation` 照常。
  **代价必须说清**:来源变成 http 后,**同机任何进程都能 GET 到仓库内的数据文件**(包括
  `data/config.json`),这是 file:// 来源下没有的暴露面;端口是随机的,地图白名单只能填 `127.0.0.1`
  (不同端口算不算同一来源,要等真实 JS API Key 才能验)。
  路径越权(`../`)那条防线**测不到于渲染层**(浏览器会先把 `/../`、`/%2e%2e/` 规范化掉),
  所以抽成纯函数 `lib/static-guard.js` 在单测里逐个边界钉住。
- **真实里程不写回 `regions.json`(决定,附理由)**:运行时已经用实时路网算,固化没有收益;
  而实测里有几条 leg 的"真实值"是**路网绕行 artifact**,固化会把它继承给"没 Key 时"的预算。
  最典型的是 `派镇→墨脱`:直线 50km,腾讯绕成 **1889km / 37.3 小时 / 186 段路**——不是有条一天能开完的路,
  而是那条近路在路网里不通。为此加了**疑似绕行提示**:某段真实里程超过两点直线 8 倍(且直线 >10km)时,
  逐日卡片与导出会写明「真实里程是直线距离的 N 倍,路网里近路可能不通,本段建议单独核实」
  (`黄柏塬→厚畛子` 23.5→258km、`转龙镇→东川红土地` 27.8→203km 同样会触发)。
- **环线不做"自动裁环"**:天数不够时只提示"偏紧"并建议加天数/减线路,不会替你砍掉节点。
  砍哪一段是产品判断(牵扯你想去哪),算法偷偷决定会生成一条"看着合理、你并不想去"的行程——
  同「距离是必要条件不是充分条件」那条纪律。要少走就自己少选线路或用机动日,不自动替你取舍。
- **GPX 的边界**:导出的驾车轨迹只在配了高德 Key 时是真实路线;没 Key 时是**环线节点直线骨架**
  (`metadata` 里明说"仅作方向参考,不能当路书用",且直线长度会比行程标称的估算里程小约 1/1.3)。
  徒步段应用内没有轨迹数据,只导出线路起点这一个路点。
  导入方向只写 `distanceKm`/`climbM`/`maxAltM` 三个字段,缺高程的 GPX 拿不到爬升与最高海拔(会被归入
  rejected 而不是写 0),与标称值差超 10% 的一律进 review、不覆盖。
- **`npm test` 会真起一个 Electron 窗口**(渲染层 DOM 冒烟)。无显示环境/远程会话里这一步可能失败,
  那不是代码坏了 —— 改用 `npm run test:unit` 跑纯函数部分,或按 `INSTINCTS.md` 的软渲染两条再跑。
  这一步不能省:单测走 `require`(有独立模块作用域),渲染层的共享作用域、script 标签缺失、
  按钮有没有接线、preload 有没有暴露对应方法,**只有真起窗口才测得到**。
- 机票价格不做(OTA 加密数据),以后用"预估 + 跳转"兜底。
- 打包后的 exe 在 `dist/Gushan-portable.exe`;重装系统或换机后先 `npm install && npm run dist`,再以管理员外的普通权限运行 `scripts/make-shortcut.ps1`(带 BOM,勿用无 BOM 编辑器重存)重建桌面快捷方式——或用等价的 `npm run shortcut`(内部就是调这个 `.ps1`,并会在 `dist/` 缺失时先提醒)。快捷方式必须由 shell 自己写:手工拼的 `.lnk` 因缺 LinkCLSID 与完整 LinkTargetIDList 会被资源管理器判为无效,桌面图标退化成一张白纸。
