## 第一部分：问题诊断（为什么现在满足不了你的需求）

### 需求还原

你的原话是：*「我是徒步爱好者，但同时也是入门，没法自己在无数指南中找到符合我要求的。」*

拆成可验证的功能需求：

| 编号 | 需求 | 现状 |
|---|---|---|
| N1 | 我能按**自己的能力**筛出走得动的线 | ❌ 完全没有 |
| N2 | 我能看到**这条线具体怎么走**（攻略级信息） | ❌ 只有一句话摘要 |
| N3 | 我知道**怎么到达**、要花多久 | ⚠️ 部分（限 35 条） |
| N4 | 我知道**这个季节去合不合适** | ⚠️ 部分 |
| N5 | 在合适的线里，按**风景和花费**排序 | ✅ 已有，且质量不错 |

**核心矛盾：软件服务的是 N5（选 scenic 的线），你卡在 N1（走不动的线）。**
推荐引擎的门槛设错了——它先按「你想看什么」筛，而不是先按「你走得动什么」筛。

### D1 · 打分公式里难度权重为 0（P0）

**证据**
- `lib/recommend.js:56-67` — `scoreOf(hitsLen, sceneryLen, est, budget)` 只有两项：
  `sceneryScore * 70 + budgetScore * 30`。`trail.grade` **未参与计算**。
- `lib/recommend.js:70-81` — `scoreTrail` 的硬过滤只有三个：`禁入/关闭`、`maxDays`、不含难度。
- `lib/recommend.js:86-101` — `rank` 的过滤只有 `excludeIds / province / maxDays`。

**实测证据**（我实跑 `lib/recommend.js`，非推测）
```
输入：scenery=['雪山'], budget=4000
  ★5 乌孙古道(7天)      score=25.7  est=¥1160
  ★1 四姑娘山·长坪沟(1天) score=98.7  est=¥360
```
一条 7 天高海拔长线能进你的候选池，只是被「贵」挤掉了，**不是被「走不动」挡住的**。

**我的思考**
- 现有的 `maxDays` 是唯一挡住长线的条件，但它是**天数**不是**难度**。存在大量「2 天但 ★5」的线，`maxDays` 完全拦不住。
- `lib/grading.js:21-39` 的 `computeBreakdown` 已经把日均里程/爬升/海拔/技术地形/重装量化了，`_grade.suggested` 已经挂在每条线路上（`electron/main.js:44` 注入）。**数据已经在手上，只是没接进 `scoreTrail`。**
- 但我不建议把难度做成打分权重（加权求和），而是做成**硬过滤**。理由：入门者看到「★5 排在第 8 位」会困惑，「★5 直接不出现」才清晰。**门槛不该参与竞争，只该做闸门。**

**改法**
`rank`/`scoreTrail` 增加 `gradeMin / gradeMax`（硬过滤，可留空），并在 `main.js` 的 handler 里把体能上限作为默认值灌进来（见 D2）。

**验收**
- 筛选 ★1–★2 后，结果里 `grade > 2` 的条数 = 0（写单测断言）。
- 不填难度时，行为与现在完全一致（不破坏既有用户习惯）。

### D2 · 体能联动代码已存在，但推荐页一次都没调用（P0）

**证据**
- `lib/fitness.js:10-20` — `ableGrade(state)`：耐力分锚定难度上限，封顶 ★4，再按爬坡分 ±1 调整。
- `lib/fitness.js:24-70` — `matchTrail(trail, state)`：输出 `fit/stretch/over` 三档 + **带真实数字的解释**（如「耐力得分 62、爬坡『偏弱』，驾驭 ★3 及以下有余」）。
- `electron/main.js:72-89` — `trails:recommend` handler 的 `input` 只解构 `budget / maxDays / scenery / province / excludeIds / limit`。**没有 `ableCap`，没有 `fitness` 调用。**
- `lib/planner.js:252-256` — 那边**已经在用** `fitness.ableGrade(bodyState)`。

**我的思考**
- 这是**最大的浪费**。78 行已经写好、有单测（`test/fitness.test.mjs` 104 行）、写得相当认真（负荷过高/训练中断/准备度低迷会自动降档，高反提示独立于体能）的逻辑，**在「帮我挑」这个环节完全缺席**，只在「我已经选定后自动选线」时生效。
- 对你尤其重要：`ableGrade` 返回 `null` 时（RunOS 没启动）设计是「宁缺毋编」，退化为不限制。所以我可以**安全地**把它接成默认值——不装 RunOS 也不影响。
- 但有个设计判断要你拍板：**接进来之后，筛选应该自动生效还是需要你勾选开关？** 我倾向自动生效（无 RunOS 时不生效），因为你的诉求就是「别让我判断」。见下方 O1。

**改法**
`main.js` 的 handler 里 `runos.fetchBodyState`（已有 10 分钟缓存）→ `fitness.ableGrade()` → 作为 `gradeMax` 的默认值；`null` 时不设限。

**验收**
- 启动 RunOS + 高耐力数据 → 推荐结果自动收窄到 ★4 以下。
- 不启动 RunOS → 结果与现在一致，不报错。

### D3 · 一日线住宿费恒为 0，落地估系统性偏低（P0）

**证据**
- `lib/recommend.js:21` — `const nights = Math.max(trail.days - 1, 0);`
- 实测：`阿布吉措`（★2，云南，1 天）→ `{lodging: 0, food: 90, tickets: 0, total: 90}`
- 同一批推荐 12 条里 **4 条 `tickets` 未标**，全部按 0 计（`lib/recommend.js:24` 的 `trail.tickets || 0`）。

**我的思考**
- `days - 1` 这个公式对「N 晚 N 天」的多日线是对的，但对**当日往返/当日走完**的一日线是错的——你人还在景区附近，住宿是实打实要花的。
- 叠加 `tickets` 未标按 0，`¥90` 这个数字对真实花费（住宿 + 往返景区交通 + 餐费，至少 ¥300+）**低估 70% 以上**。
- 这条已经进入 `README:53` 明文写的口径（「未标注按 0 并在卡片言明」），但**卡片并没有真的言明**——`src/app.js:1136` 只显示 `预计人均 ¥${est}`，没有任何「门票未知」的提示。**文档承诺了 UI 没兑现。**

**改法**
- `nights`：一天线按 1 晚计（即 `days === 1 ? 1 : days - 1`，需要你确认口径，见 O2）。
- 未标 `tickets` 时：估算里标注为「门票未标注」，卡片显式出灰色提示，而不是静默按 0。

**验收**
- 阿布吉措落地估从 ¥90 变为 ≥ ¥290（住宿 200 + 餐饮 90）。
- 单测：未标 tickets 的线路，`costBreakdown` 返回带 `ticketsUnknown: true`。

### D4 · 152 条线路推荐出来却用不了（P1）

**证据**
- `data/trails.json` 实测：`regionId` + `node` 双字段齐全的只有 **35/187 条（18.7%）**。
- `src/app.js:1022-1023` — `data-plan` 按钮**只在 `t.regionId` 存在时**渲染。没有 → 按钮不出现。
- 实测：推荐 12 条里 **8 条没有规划按钮**（阿布吉措/丹巴/雨崩/太白山 4 条有，另 8 条没有）。

**我的思考**
- 这是「选出来了却用不了」的挫败感来源，比推荐不准更伤。
- 但**不应该**简单地把 152 条过滤掉——那些线路本身是好数据，砍掉是浪费。
- 正确的做法是**分级呈现**：能规划的给「一键规划」；不能规划的明确标「需自驾车/包车直达，本次不含交通」，让你知道它仍然可选、只是规划器覆盖不到。
- 另一条思路：`regionId` 缺失本质是「这条线属于哪个环线区域」没标。这可以脚本化回填（按 province+area 匹配），但**需要人工确认**，不能自动猜。见 P1-补数据。

**改法**
卡片加一个「规划器未覆盖」的明示标签 + hover 说明原因；不改变现有过滤逻辑。

**验收**
- 推荐结果里不可规划的线路，100% 带明确标签，不再是「静默没按钮」。

### D5 · 「教我怎么走」的内容基本为零（P1）

**证据**
- `src/app.js:1015-1017` — 卡片详情只有 `risks`（风险）、`supplies`（补给）、花费三项。
- 缺：路线轨迹/关键节点、典型日均里程与爬升、最长无补给段、往返交通方式与耗时、季节性提醒的具体化。
- `lib/gear.js` 有 `gearChecklist`，但只在**生成行程后**（`planner.js:379`）才用，浏览路线库时看不到装备清单。

**我的思考**
- 你说「没法在无数指南里找到符合要求的」，这里还有第二层意思：**即使选定了，也不知道怎么准备**。
- 对入门者，最需要的其实是三个数：**日均要走多少公里 / 爬升多少米 / 最长一段多久没补给**。这三个数不需要新数据源，`distanceKm / climbM / days` 已经全有了（187/187 覆盖），只是没算成「每天」的粒度展示。
- 装备清单同理，可以复用 `gear.js`，不需要重写。

**改法**
卡片详情增加一个「入门速览」块：日均里程、日均爬升、最高海拔、最长无补给天数（`supplies` 文本 + `days` 推断，宁缺毋编则留空）。

**验收**
- 任意 ★1–★2 线路卡片，能直接回答「一天走多少、要爬多少、背多重」。

## 第三部分：需要你拍板的开放问题

**Q1 · 难度筛选默认生效还是需勾选？**
- A：自动生效（接入 RunOS 就自动收窄，不接则不限制）—— 我倾向这个，最贴合「别让我判断」
- B：表单默认「★1–★3 安全档」，用户可改
- C：只做手动下拉，不自动

**Q2 · 1 天线路的住宿怎么算？**
- A：按 1 晚算（我倾向这个，贴合现实）
- B：1 天线一律按 0 晚（视为当日往返，但需在卡片注明「不含住宿」）

**Q3 · 这次改动的范围？**
- A：只做 P0（64 行，直接解决「走不动」+ 预算失真）
- B：P0 + P1（让 152 条线路也有明确出口）
- C：P0 + P1 + C1 重名修复

**Q4 · 体能上限封顶 ★4 还是 ★5？**
现有 `fitness.js:19` 硬封顶 ★4（★5 极限线不给自动放行）。我认同这个保守设定，但如果你的目标就是冲极限线，这个上限会让你够不着——需要你确认是否保留。

## 第四部分：我的整体判断

**它现在是一个「行程生成器 + 半成品选线器」，而你要的是一个「选线器」。**
它的行程拼装能力（12306 实时票价、高德真实路线、油价实价、天气避让、装备清单）非常扎实，但**这些能力全都建立在「你已经选定了线路」的前提上**——而你卡的地方恰恰是选定之前。

好消息是：**你需要的 80% 已经在仓库里了，只是没接线。**
`fitness.js` 78 行体能逻辑、`grading.js` 量化评级、`gear.js` 装备推导、全部 187 条线路的距离/爬升/海拔数据——都现成。缺的是把它们从「选定之后才生效」挪到「选定之前就参与筛选」。

成本诚实说：P0 约 64 行代码、零新增数据、零新依赖、零 UI 大改。这是我见过性价比最高的一次改动。
