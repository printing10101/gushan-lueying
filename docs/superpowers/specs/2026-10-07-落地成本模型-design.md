# 落地成本模型：分项化 + 季节系数 + 一次性开销

> 状态：已批准（2026-10-07）
> 上游：`lib/recommend.js:costBreakdown`、`lib/planner.js:stayBudget`、`data/regions.json`
> 相关教训：`INSTINCTS.md`（deepEqual 深比较、渲染进程共享作用域、数据文件手工格式）

## 1 问题

用户原话：*「怎么感觉这个人均落地的费用就没有变过，一直都是一个样子的」*

**这是真的，而且是结构性的。** `costBreakdown`（`lib/recommend.js:21`）只读三个变量：

```
住宿 = round(晚数 × 房费 ÷ 每房人数)      晚数 = days<=1 ? 1 : days-1
餐饮 = days × 人均餐费
门票 = trail.tickets ?? 0
```

实测（2026-10-07，`node -e` 跑全库）：

| 现象 | 数字 |
|---|---|
| 全库线路 | 191 条 |
| 落地总额的不同取值 | 65 个 |
| 其中 `¥180` 一档 | **25 条**，全部是「1 天 + 无门票」线 |
| 「雪山 + ≤3 天 + ★≤3」前 5 条 | 180 / 190 / 200 / 200 / 200 |

**根因**：`¥180` = 住宿 100（默认 200/晚 ÷ 2 人）+ 餐饮 80（默认 80/天），与城市无关。凡是 1 天、无门票、区域无独立基准的线，算出来都是不多不少 ¥180——阿坝、香格里拉、深圳都一样。

**并且它不读用户的任何输入**：人均预算、最多天数、出发站、难度、省份、景色，全都进不了这个公式。所以换滤镜、调预算，这个数一动不动。

## 2 目标与非目标

**目标**

1. 落地估算随 **出行日期 / 出行人数 / 住宿档次** 变化，且变化有据可查。
2. 把"不知道"变成一等公民：数据缺失显式标 `未含`，不写 0 冒充。
3. 推荐页与行程规划页共用**同一套**预算口径，消除两份公式的静默漂移。

**非目标（明确不做，附理由）**

| 不做 | 理由 |
|---|---|
| 抓真实市场房价 | 已证伪，见附录 A |
| 区域"住宿城镇"字段 | 那是抓价与系数的锚点；抓价砍掉后锚点就是区域本身 |
| 「大型活动」日历（音乐节等） | 无可查证来源，编不得 |
| 向导/马帮/租赁/保险的**金额**估算 | 同上，只列清单不给数 |
| 进山费/观光车的**估算金额** | 只补真实数据（第 6 节）；没有数据的线不产出该条目，绝不估一个数 |

## 3 决策记录

| 决策 | 选择 | 依据 |
|---|---|---|

## 4 架构

### 4.1 新增 `lib/budget.js`（零依赖，双端导出）

遵守 `INSTINCTS.md` 的渲染进程约束：导出名文件级唯一（`api_budget`），尾部 `module.exports` + `window.GushanLib` 双端导出，`src/index.html` 加对应 `<script>`，`src/app.js` 用**加前缀解构**。

```js
// 住宿：单点函数，nights 由调用方给（见 4.2 语义分离）
stayCost({ nights, headcount, perRoomPerNight, peoplePerRoom, tierFactor, seasonFactor })
  → { name, amount, note }

// 餐饮
foodCost({ days, headcount, perPersonPerDay, seasonFactor })
  → { name, amount, note }

// 门票：未标 → amount:null（不是 0）
ticketItem(trail, { headcount })

// 进山费/观光车：仅当线路库有该可选字段时才产出条目
extraFeeItems(trail, { headcount }) → Item[]

// 组装：推荐页入口（按"徒步"语义算晚数：1 天线算 1 晚）
landBudget(trail, { date, headcount, tier }, cfg)
  → { items, total, knownCount, unknownCount, notes }
```

行程规划侧**不新增组装函数**：`planner.stayBudget` 直接调 `stayCost` + `foodCost`（它有自己的预算表结构，多包一层没有收益）。

`Item = { key, name, amount: number|null, note: string, source: 'calc'|'data'|'unknown' }`

`source` 表示这个金额是怎么来的：`calc` = 按公式与系数估的；`data` = 线路库里标明的实数（如 `tickets`）；`unknown` = 数据缺失，此时 `amount` 必为 `null`。UI 据此决定哪几行要向用户明示"这是估的"。

**不变量**

- `amount === null` 表示未知。**任何情况下都不写 0 冒充未知**（`INSTINCTS.md` 的 `Number('')===0` 与 `grading.usable:false` 两条教训）。
- `total` 只累加 `amount !== null` 的项；`unknownCount` 一并返回，卡片据此挂"未含"提示。
- 每个 `note` 必须写清口径来源（如 `舒适档 ×1.4 秋色旺季`、`区域基准(川西环线)`）。

### 4.2 语义分离：`nights` 由调用方给

这是收敛口径的关键。现状是**两份公式各写一遍**：

- `lib/recommend.js` 的 `costBreakdown`：`days===1 ? 1 : days-1`（徒步晚数）
- `lib/planner.js` 的 `stayBudget`：`Math.max(days-1, 0)`（行程晚数）

两者语义本就不同（徒步天数 vs 行程总天数）。`INSTINCTS.md:42` 记过一次同类后果：`nights = max(days-1, 0)` 对 1 天线恒为 0，落地估系统性低估（阿布吉措 ¥90 vs 实际 ≥¥290）——那次修的是公式自身的边界漏判。而两份实现并存，真正的问题是让这类漏判**只在一处被修好、另一处继续错**：本次实测里 `recommend.js` 已经改成"1 天线算 1 晚"，`planner.js` 却还是 `max(days-1, 0)`。

改法：**只留一个 `stayCost`，`nights` 由调用点算好传进来**。差异从此写在调用点，一眼可见，不会再有两份实现对不上。

### 4.3 新增 `data/seasonality.json`（只装能查证的季节事实）

```json
{
  "_说明": "住宿/餐饮季节系数。按「出行日期 + 区域」收集全部命中项,取最大值,不叠乘。系数是估的,卡片必须标注来源。",
  "months": { "1": 0.9, "2": 0.9, "7": 1.3, "8": 1.3, "_说明": "全国性淡旺:寒假 1-2 月、暑期 7-8 月" },
  "holidays": [
    { "label": "元旦", "from": "2026-01-01", "to": "2026-01-03", "lodging": 1.2, "food": 1.1 },
    { "label": "春节", "from": "2026-02-15", "to": "2026-02-23", "lodging": 1.6, "food": 1.2 },
    { "label": "清明", "from": "2026-04-04", "to": "2026-04-06", "lodging": 1.3 },
    { "label": "劳动节", "from": "2026-05-01", "to": "2026-05-05", "lodging": 1.5 },
    { "label": "端午", "from": "2026-06-19", "to": "2026-06-21", "lodging": 1.3 },
    { "label": "中秋", "from": "2026-09-25", "to": "2026-09-27", "lodging": 1.3 },
    { "label": "国庆", "from": "2026-10-01", "to": "2026-10-07", "lodging": 1.8, "food": 1.2 }
  ],
  "regions": {
    "chuanxi": { "label": "川西秋色旺季", "months": { "10": 1.4, "11": 1.2 } },
    "yili": { "label": "伊犁花季", "months": { "6": 1.3 } }
  }
}
```

**字段约定**：`lodging` 必需；`food` 可选，缺省 1.0（**不跟随住宿系数**——住宿涨得比吃饭猛，两者分开是刻意的）。加载时**跳过所有以 `_` 开头的键**（`months` 里那个 `_说明` 不是月份，不能被当成 1 号月份；这是本项目 `config.example.json` 已有的写法惯例，但读取方必须显式跳过）。

**2026 年放假安排来源**：国务院办公厅《关于 2026 年部分节假日安排的通知》，经央视新闻 2025-11-04 转载核对（https://news.cctv.com/2025/11/04/ARTIzBycPZbvvPD4uW0iYbKR251104.shtml ）。**录入时须以中国政府网 gov.cn 原文再核一遍**（本次 gov.cn 页面有 301 重定向环、抓取失败，未能二次核对）。

**系数取值规则：取所有命中项的最大值，不叠乘。**

理由：国庆正好落在川西秋色旺季，若按"优先级命中即返回"，这条线会取到区域系数 1.4、把节假日的 1.8 压掉——那恰恰是最贵的时候。叠乘又会把系数推到一个没有依据的高度（1.4×1.8=2.52）。取最大值既简单又可预测，也避开了"一拍脑袋的运算"：`max(1.4 秋色, 1.8 国庆) = 1.8`。

命中来源（每一路都要能报出来，取用的那一路写进 `note`）：

1. `regions[regionId].months[月]` —— 区域专属旺季
2. `holidays[]` 覆盖该日期的条目 —— 法定节假日
3. `months[月]` —— 全国性淡旺
4. 都没命中 → 1.0

`regionId` 只有 100/191 条有（`data/trails.json` 实测），其余线路只走第 2、3 路。

**降级规则**

- 出行日期留空 / 非法 → 全市 1.0，卡片注明"未填出发日期,按中性基准"。
- 年份超出 `holidays` 覆盖范围 → 只走 `months`，卡片注明"节假日日历未覆盖 YYYY 年,仅按月份"。
- `regions` 里出现库里不存在的 `regionId` → 由 `seasonality-data.test.mjs` 拦下（见第 7 节）。
- 系数一律是估的，卡片必须让用户看见用的是哪一档。

### 4.4 档次系数放哪

放 `lib/budget.js` 的代码常量（`TIER_FACTORS = { 经济: 0.6, 舒适: 1.0 }`），可被 `cfg.lodging.tierFactors` 覆盖。

**不放 `data/config.json`**：该文件已在 `.gitignore:3`，放进去就不会被版本控制、也无法写测试。`config.json` 是机器私有配置，模型口径应该入库——这与 `regions.json` 里 `stay` 基准入库是同一条理由。同时在 `data/config.example.json` 的 `lodging._说明` 里补一句"可用 tierFactors 覆盖档次系数"。

### 4.5 一次性开销清单（不进人均数字）

新增 `oneTimeCosts(trail, { date, headcount })`，纯推导，**只列"要不要准备"，不给金额**。判据字段全部是线路库里已实测存在的：

| 触发条件（字段与判据） | 清单项 | 文案 |
|---|---|---|
| `days >= 3` 且（`supplies` 含"无补给" 或 `type` 含"重装"） | 向导 / 马帮 / 背夫 | 「需另询当地价」 |
| `maxAltM >= 3500` 或 `techLevel >= 3` | 高原保险 / 应急药品 | 「按保额与人数另计」 |
| 出行日期落在 12/1/2 月，或 `bestMonths` 含 12/1/2 | 装备租赁（冰爪 / 雪套） | 「按日租，另计」 |

字段覆盖实测（191 条）：`days`/`supplies`/`type`/`maxAltM`/`techLevel` 均 191/191，`bestMonths` **仅 177/191**——缺 `bestMonths` 的线路只走日期判据，不猜季节。**不引入任何新数据源。**

三个新控件的默认值：

| 控件 | 默认 | 留空/缺省时 |
|---|---|---|
| 出发日期 | 空 | 全市系数 1.0，卡片注明"未填出发日期，按中性基准" |

**这里有一处必须说清的行为变化：默认值下这个数字会变高，它是修 bug，不是回归。**

旧公式硬写 `perRoomPerNight ÷ 2`，等于假设"永远 2 人同行"；一个人去也得包整间房。所以一条 1 天无门票线会从 **¥180**（100 住宿 + 80 餐饮）变成 **¥280**（200 + 80）。

这与 `planner.js` 一直在用的 `rooms = ceil(headcount / peoplePerRoom)` 是同一个算法——**是推荐页在错、planner 在对**。改完两侧口径才真正统一。默认人数取 1 也与规划页表单的 `value="1"` 对齐。

## 8 验收标准

1. 「雪山 + ≤3 天 + ★≤3」的 12 条结果，落地值不再集中在 180–200：填不同出发日期（如 10-01 国庆 vs 11-15 平日）时，同一条线的数字**必须不同**，且卡片写明系数来源。
2. 出行人数从 1 改到 2，同一条线的住宿项**必须减半**（1 人承担整间房）。
3. 住宿档次从"舒适"切到"经济"，住宿项按 ×0.6 变化且卡片标注档位。
4. 任意缺门票的线，卡片显示"未含·需自核"，而不是静默按 0。
5. `npm test`（lint + 全部单测）全绿。
6. 真机起 Electron 窗口看控制台无 `SyntaxError`（渲染进程共享作用域的历史坑）。
7. 默认值下（日期留空 / 人数 1 / 舒适档）一条 1 天无门票线显示 **¥280**（住宿 200 + 餐饮 80），卡片注明是「1 人整间房」——即第 5 节那处刻意的行为变化确实发生了，且被言明而不是悄悄改掉。

| 2 | 阿坝县 / 香格里拉 / 丽江 | 页面正常渲染，但卡片价全被"登录以查看会员价"遮罩 → **0 个价** |
| 3 | preload 拦截 fetch/XHR | 页面先被重定向到 `passport.ctrip.com/user/login`，仅捞到 config 类 JSON |
| 4 | 成都 · 第 2 次（约 10 分钟后） | ❌ 同城同参数，被弹到"登录首页" + `captcha: true` |

**结论**：三条硬事实——(1) 单次 30 秒，成本高；(2) 未登录时多数城市读不到价；(3) **连续 7–8 次后被风控升级，且是在用户自己的机器与 IP 上失效**。要绕过就得在应用里登录携程账号并持久化 cookie，那是账号风险 + 隐私的账。

**决策**：放弃抓价，退回本地季节系数（第 3 节决策记录第 1 行）。
